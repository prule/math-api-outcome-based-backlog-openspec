Outcome backlog: vibe coding vs OpenSpec

The same PRD, domain model and standards as the earlier two-build comparison, but this time the backlog states outcomes ("who gets what, and how we will know") and leaves the design to the builder. One agent, Claude Opus 5.5, built it twice. The vibe build went straight from each outcome to code. The OpenSpec build ran /opsx:propose, /opsx:apply, /opsx:verify and /opsx:archive around the same code. Both ran the same /ponytail:ponytail-review and /code-review, wrote retrospectives, and merged each item by PR on green CI.

Short answer

The time gap shrank, but the token gap didn't. OpenSpec still did slightly better on contract correctness. With an outcome backlog, the OpenSpec build spent 1.16× the active time of the vibe build on items 2–5 (46.4 against 40.1 minutes), down from 1.52× with the task backlog. It still used 1.43× the output tokens. Most of the narrowing came from the vibe build slowing down, because it now had to choose its own design: 40.1 minutes, up from 32.6.

Both builds wrote the same BR-1 bug as last time, Math.abs(scale), which lets a scale of Integer.MIN_VALUE through. Again only the OpenSpec build fixed it. This time it caught the bug itself while building, seconds after its domain tests passed, and its design.md had stated the rule as -1000 ≤ scale ≤ 1000. The vibe build shipped the bug, but it can't be reached over HTTP: Jackson 3 rejects that exponent while parsing, so both jars return 400.

Otherwise the two came out level, and each did better in different places. The OpenSpec build follows the PRD more literally. Its framework errors carry type, it rejects "operation": 123 as an invalid request, and it counts the body limit in characters, as the PRD says. The vibe build is 15% smaller, with 95% branch coverage against 82.5%, and it documents its 406, 415 and 500 responses with examples that are checked against real responses. To meet the body limit it changed the PRD from "characters" to "bytes", so one yaml block did the job instead of 64 lines of code. Sonar passed both, with one code smell each.

Neither build ran without help. The vibe build paused once before /code-review, and that led to the "don't stop between steps" rule in its CLAUDE.md. After that, every item needed a "Check and merge", because the auto-mode safety check blocked the CI monitor and the merge. The OpenSpec build found an ordering bug in its own process on item 1: archive needs the CI task ticked, and CI only runs once a PR exists. That bug became process PR #2, "open the draft PR before archive". The build then needed repo settings for auto-merge and branch protection, and a manual merge twice when GitHub armed auto-merge but never fired it.

Caught in both

  • Item 2, ponytail: unplanned exceptions fell through to Spring Boot's /error JSON, not Problem Details. Both builds reproduced it with the same scale-overflow multiply, and both added a catch-all 500.
  • Item 5, standards (hard): BR-1 limits copied into OpenAPI annotations, against STANDARDS §4. Both fixed it by generating the text from domain constants.
  • Item 5: springdoc's ProblemDetail schema has a properties field that Spring never sends. The vibe agent found it by reading the spec JSON. In the OpenSpec build, the spec reviewer found it.

Caught only in openspec

  • Framework errors carry no type (404, 405, 406, 415). PRD §3.2 says every error has one. /opsx:verify asked for the 405 and 415 bodies to go through the same Problem Details checks, and the tighter tests then failed on $.type. The vibe build left the field out on purpose (retro 2: "framework errors have no PRD type"). That is valid under RFC 9457, but it isn't what the PRD says.
  • "operation": 123 coerced to the string "123" and reported as unknown-operation. The OpenSpec spec reviewer confirmed it against the running app, and the fix was a Jackson coercion config. The vibe build still does this. Its spec reviewer has the same brief, so this one comes down to chance, not to OpenSpec. It was the vibe reviewer that caught this in the task-backlog round.
  • Body limit in UTF-16 units and the wrong charset (item 4, spec reviewer). This only applied because the OpenSpec build kept "characters" and wrote its own counter. The vibe build changed the PRD to bytes and let Jackson count.
  • "From the docs alone" read literally (item 5, spec reviewer): the docs pointed readers to "BR-3" and "PRD §3.2 order". They now state each rule. A few BR ids are still left in example summaries, although statesTheRulesAClientNeeds says none remain. That test checks the description, not the examples.

Caught only in vibe

  • Hand-written examples could drift from real responses (item 5, ponytail). The vibe build added a test that replays every example and compares the whole body, and on its first run it found the 415 example was wrong. The OpenSpec build built its examples from exception messages, then added a replay test as a backstop.
  • Undocumented 406 (item 5, spec reviewer). It's now documented with a checked example. OpenSpec documents 404, 405, 415 and 500 only in prose, with no response entries.

What /opsx:verify added

It made 8 findings over five items. Five were the same process artefact: "the CI task isn't ticked", which is true of every item until the PR runs. The other three were a hand check standing in for a formatting test, a redundant ArchUnit rule, and the 405/415 assertion gap that led to the missing type. That last one is the only verify finding that changed behaviour. Verify ran in the main session, so its cost is part of OpenSpec's extra time.

The repeat bug

Math.abs(scale), third build in a row

BR-1 caps an Operand's scale at ±1000. new BigDecimal("1E+2147483648") has scale Integer.MIN_VALUE, and Math.abs of that is still negative, so a Math.abs(scale) > 1000 check lets it through. All four builds so far wrote that line: both task-backlog builds and both outcome-backlog builds.

  • openspec: design.md said -1000 <= scale() <= 1000. The agent wrote Math.abs anyway. Seconds after the domain tests passed, it noted "I found a bug in my own code", confirmed it with a one-line Java program, and fixed it with a test. Last time the code reviews caught it. This time no review needed to.
  • vibe: shipped with Math.abs(operand.scale()) > MAX_SCALE in Calculation. None of its three reviews flagged it. Over HTTP it can't be reached on this stack: Jackson 3 rejects 1E+2147483648 (as a string or a number) while parsing, so both jars return 400 invalid-request. It is a latent domain bug, which turns live if the parser ever passes such a value through. In the task-backlog round, the same input reached the domain and returned 500.

It's one data point, but it points the same way as last time. Having the rule written down as two comparisons is what got the agent to notice it had written something else. Neither build's reviewers found the bug on their own in either round.

Retrospectives

What each build learned

vibe

  • Add only what a "done when" check needs (item 1: validation starter, layer marker files).
  • Write tests first and watch them fail. It started from item 3, and from item 4 the red step had to be a failing assertion, not just a compile error.
  • Probe the running jar with hostile input during the build (items 2, 4), also with a small heap.
  • Check docs against real responses, not against themselves (item 5).

openspec

  • Check what the framework already does before writing a non-goal (item 1).
  • Probe the running app with hostile-but-valid JSON during apply (item 2).
  • When a check guards an int, test Integer.MIN_VALUE (item 4).
  • Pin down "characters" at propose time (item 4). Read the outcome literally (item 5).

The lesson both builds recorded most was the same as in the task-backlog round: probe the running app, and don't trust framework defaults (Spring 7, Jackson 3, springdoc). OpenSpec's propose step didn't prevent those surprises. They showed up in tests or probes in both builds. Neither build has written its probing habit into a test or a process step, so each new session relearns it.

Caveats

What makes this comparison unfair

  • One run each. The same model can write a bug and then catch it or miss it by chance. The coercion catch went to vibe last round and to OpenSpec this round, with the same reviewer brief.
  • Not a clean sample. Both outcome builds came after two task-backlog builds made from the same docs, and those docs already contained many of their decisions. The OpenSpec build also started after the vibe build was finished.
  • Different session shapes. The vibe session paused for 8.5 hours before item 5, so its cache expired. Item 1 in both builds includes some one-off process and repo setup.
  • The findings tally counts bullets. It shows how much each build looked at, not how many bugs each found.
  • No plan review. Unlike the earlier OpenSpec build, this process has no review of the proposal before apply, so the plan got its first critical read only after the code was written.
Takeaways

So, does OpenSpec add more with an outcome backlog?

  • A little more, at a lower relative time cost. When the backlog leaves the design open, the vibe build pays for design too. OpenSpec's time overhead fell from 52% to 16%, but its token overhead stayed at about 40%.
  • The written design keeps paying off on exact rules. In both rounds, the only build to fix the BR-1 bug was the one whose design stated the rule as two comparisons.
  • The PRD was followed more literally. OpenSpec kept "characters" and wrote code for it. The vibe build changed the contract to fit Jackson. Both are allowed by CLAUDE.md, but they are different kinds of decision. A vibe build is more likely to bend the spec to the tool.
  • /opsx:verify did little: one behavioural catch in five items, plus a recurring false alarm about the CI task. Changing its brief or the order of steps would remove the false alarm.
  • The plan is only as good as its review. Eleven scenarios were added after code review. Bringing back a plan review, or asking propose to settle units and boundaries such as "characters" and int limits, is the cheapest way to make the plan do more.
  • Follow-ups for the vibe build: replace Math.abs with a two-sided range check and test it at 1E+2147483648 in the domain; add type to framework errors, or record the RFC reading in the PRD; decide whether "operation": 123 should be invalid-request. For the OpenSpec build: remove the leftover BR ids from example summaries and extend statesTheRulesAClientNeeds to cover examples.
